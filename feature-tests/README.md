# 功能测试说明

> 目录用途：存放各功能模块的功能测试用例与运行脚本
> 建立日期：2026-09-21
> 上级文档：[../README.md](../README.md)、[../../PROJECT_CONTEXT.md](../../PROJECT_CONTEXT.md)

---

## 一、这个目录测什么

功能测试回答的问题是"**这个功能到底能不能跑通、跑出来的结果对不对**"，面向单条完整功能链路，而不是单个函数的内部逻辑。

与另外两处测试资产的分工：

| 位置 | 测什么 | 样本 | 是否入仓库 |
|---|---|---|---|
| `backend/tests/` | 单元测试：单模块、单函数，含架构依赖检查 | `backend/tests/fixtures/` 固定样本 | 是 |
| `feature-tests/`（本目录） | 功能测试：一条功能从输入到产出走通，判据可判定 | `devdata/` 开发期数据 | 是（脚本与记录），原始数据否 |
| `tmp/` | 一次性探针脚本，验证完即弃 | 随手取 | 否 |

三条界线必须守住：

1. **功能测试不替代单元测试。** 单元测试守着每个模块的内部正确性，功能测试守着模块拼起来之后链路是否成立。某条功能测试挂了，先跑对应单元测试定位是哪个模块的问题。
2. **本目录不写探针脚本。** 探针属于阶段0，验证完就该删掉；写进本目录的必须是需要重复运行、能长期回归的。
3. **不把业务数据放进本目录。** 数据从 `devdata/` 取，本目录只存脚本与记录。骑行文件含 GPS 与心率，属个人数据，不入仓库。

## 二、判据从哪来

功能测试必须存在**可判定的真值**，不允许用"看起来正常"当判据。按项目约定，真值来源只有三类：

| 来源 | 适用功能 | 说明 |
|---|---|---|
| 手算黄金样本 | 领域计算：NP、IF、TSS、TRIMP、功率曲线、区间划分 | 手工核算出的数值，容差明确写出 |
| 外部权威数值 | 数据访问层：解析与活动摘要 | Garmin Connect 页面数值、文件 session 字段，注意先固定时长口径 |
| 规则约束 | 流程编排：计划生成、审核、反馈调整 | 审核能否决不合格计划、休息日偏好是否被遵守等可断言条件 |

对应项目文档的三道关（数据具备性、外部依赖可得性、技术可达性）与三档判定（可实现、有条件可实现、不可实现），本目录用例的每条结果都必须落到某一档，不允许写"应该可以"。

## 三、目录组织约定

一个功能一个子目录，子目录名用功能名的小写下划线形式，与业务模块同名。

```
feature-tests/
├─ README.md                      本文件
├─ metrics/                       例：指标计算
│  ├─ run.py                      该功能的运行入口
│  ├─ cases.md                    用例清单与记录
│  └─ expected/                   手算黄金样本（数值以文本或 CSV 存）
└─ <feature_name>/
   ├─ run.py
   ├─ cases.md
   └─ expected/
```

约定：

- 每个子目录的 `run.py` 必须能独立运行，不依赖其他子目录先跑过。命令统一为 `python feature-tests/<feature>/run.py`，退出码 0 表示全过、非 0 表示有用例未过。
- 运行结果打印到标准输出，同时写一份 `result.json` 到该子目录，便于对比历次结果。
- 中间产物只允许落在该子目录的 `output/`，不散落到仓库其他位置。
- 脚本用到的路径、用户参数（FTP、体重、最大心率）一律从命令行参数或环境变量读，不写死在脚本里。

## 四、用例记录模板

每个功能的 `cases.md` 按下表逐条记录，一行一条用例：

| 用例编号 | 功能点 | 输入 | 判据与容差 | 期望值 | 实测值 | 判定 | 备注 |
|---|---|---|---|---|---|---|---|
| MET-01 | 标准化功率 | 手算样本 30 秒窗口 | 与手算值差 ≤ 1W | 【待填】 | | | |
| MET-02 | 训练压力分数 | 某活动清洗后数据 | 与 Garmin 数值差 ≤ 2% | 【待填】 | | | |

规则：

- 期望值不确定的写【待确认】并在备注写明待谁确认，不要先填一个数再倒推。
- 判定只有三档：通过、未通过、不可判定（写明原因）。**不可判定不算通过。**
- 数据缺失导致指标不可计算的情况，本身就是一条用例，判据是"是否正确地标记为不可计算"，而不是硬凑一个数。

## 五、运行与前置条件

首次运行前需要确认的东西，在本节逐条列明（随实际落地补充）：

- Python 环境由 `uv` 管理，见项目文档 6.1，本目录不单独装依赖。
- 数据源位于 `devdata/`，路径通过参数传入。
- 涉及大模型的用例需要可用的 API Key，一律从环境变量读取，不写入任何文件；无 Key 时对应用例标记为不可判定，不静默跳过。

## 六、纪律

1. 一条功能没找到真值，就不算测过，也不允许在记录里写成通过。
2. 用例失败先看是不是数据或口径问题（例如时长口径、清洗规则），确认后再改算法。
3. 判据一旦定下不要为了让用例变绿而放宽。要改容差，先说明理由并更新 `cases.md`。
4. 涉及项目级决策的改动（表结构、层间依赖、目录结构），先改 `PROJECT_CONTEXT.md`，再改本目录的脚本。
